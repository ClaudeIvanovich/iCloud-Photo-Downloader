# Архитектура и принцип работы

Состояние на 15.11.2026: готовы все три этапа MVP: ядро, окна и трей, сборка с установщиком. Программа проверена на реальном аккаунте iCloud (вход, список, загрузка 320 файлов). Что осталось непроверенным, перечислено в разделе «Что проверено и что нет».

## Что делает программа

Берёт из iCloud Photos фото и видео, снятые в заданный период, и раскладывает их в выбранную папку:

```
<корневая папка>\
  2023\
    03 March\
      Full size\   IMG_1234.HEIC  IMG_1234.MOV  IMG_1234_edited.JPG
      Compact\     IMG_1234.jpg   IMG_1234_edited.jpg
  Unknown date\Full size\         ← снимки без какой-либо даты
  _incoming\                      ← временная, исчезает в конце задания
```

В iCloud программа ничего не меняет. Скачанные файлы не перезаписывает и не удаляет.

## Три слоя

```
            ┌────────────────────────────────────────────┐
            │  ui                                        │
            │  окна, трей, диалог 2FA, Controller        │
            ├────────────────────────────────────────────┤
            │  cli.py   отладочная командная строка      │
            └───────────────┬────────────────────────────┘
                            │ SyncEngine.run(period), pause/stop, события
            ┌───────────────▼────────────────────────────┐
            │  sync_engine                               │
            │  engine      задание: сверка и загрузка    │
            │  capture     время съёмки, период          │
            │  path_builder  папки и имена               │
            │  filters     что качать, настройки, план   │
            │  state_db    SQLite                        │
            │  compact     JPG-копии                     │
            │  fs          длинные пути, .part, публикация│
            └───────────────┬────────────────────────────┘
                            │ интерфейс ICloudClient (только чтение)
            ┌───────────────▼────────────────────────────┐
            │  icloud_adapter                            │
            │  PyiCloudClient   настоящий iCloud         │
            │  FakeICloudClient тесты и разработка       │
            └────────────────────────────────────────────┘
```

Правила зависимостей:

- `icloud_adapter` — единственное место, где есть знание об iCloud и импорт библиотеки `pyicloud_ipd`. Наружу он отдаёт простые структуры (`Asset`, `AssetVersion`, `Album`, `LoginResult`) и свои ошибки с готовым русским текстом.
- `sync_engine` не знает ни про Qt, ни про устройство iCloud. Он работает с любым `ICloudClient`, поэтому весь проверяется на `FakeICloudClient`.
- Интерфейс общается с движком тремя способами: вызывает `run`, вызывает `pause`/`resume`/`stop`, получает события через один callback. Окна при этом не обращаются ни к движку, ни к iCloud напрямую, только к `Controller`.

Рядом со слоями лежат общие модули: `config.py` (папки приложения и `config.json`), `accounts.py` (пароли в Windows Credential Manager), `logging_setup.py` (логи без секретов), `strings.py` (все тексты для пользователя на русском и переключение языка; переводы в `locales/`).

## Где что хранится

| Что | Где |
| --- | --- |
| Настройки и список аккаунтов | `%APPDATA%\iCloudPhotoDownloader\config.json` |
| Сессия iCloud (cookies, токены) | `%APPDATA%\iCloudPhotoDownloader\sessions\<account_id>\` |
| Состояние синхронизации | `%APPDATA%\iCloudPhotoDownloader\state\<account_id>.sqlite` |
| Пароль | Windows Credential Manager, запись `iCloudPhotoDownloader` |
| Логи | `%LOCALAPPDATA%\iCloudPhotoDownloader\logs\app.log`, 5 файлов по 10 МБ |

`account_id` — первые 16 символов SHA-256 от Apple ID, чтобы адрес почты не попадал в имена папок.

## Слой iCloud

### Интерфейс

`ICloudClient` содержит вход (`login`, `submit_2fa_code`, `request_sms_code`, `submit_sms_code`, `is_session_valid`), чтение медиатеки (`list_albums`, `count_assets`, `iter_assets`) и `download`. Методов, которые что-то меняют или удаляют, нет, и тест следит, чтобы они не появились.

### Что такое ассет

`Asset` — один снимок или ролик: ID, исходное имя файла, тип (фото или видео), момент съёмки в UTC, дата добавления, смещение часового пояса съёмки в секундах (если iCloud его отдал), признаки «скрыт» и «удалён» и набор версий. Версий до трёх: оригинал, видеочасть Live Photo, отредактированная. У каждой известен размер в байтах.

### Настоящий клиент

`PyiCloudClient` оборачивает библиотеку из `icloudpd` 1.33.0.

- **Вход.** Сначала пробуется сохранённая сессия, без пароля. Если её нет или она истекла, нужен пароль, затем код 2FA с устройства или из SMS. После входа пароль в памяти не остаётся.
- **Список.** iCloud отдаёт «Все фото» по дате съёмки, от старых к новым, страницами по 200 записей. Чтобы не листать медиатеку с начала, клиент двоичным поиском находит позицию, с которой начинается период, и прекращает перебор, когда целая страница оказалась позже конца периода.
- **Скачивание.** Клиент пишет поток в файл, который назвал движок, и после каждого куска вызывает callback. Через этот callback движок считает прогресс и прерывает загрузку при остановке.
- **Ошибки.** Все исключения библиотеки и сети превращаются в типизированные: неверный пароль, истёкшая сессия, ADP, выключенный веб-доступ, нет сети, сервис перегружен. У каждой есть текст для пользователя и признак «имеет смысл повторить».

## Как работает задание

Задание — это период дат «с» и «по», обе границы включительно. Одновременно выполняется одно.

```
run(period)
 ├─ проверки: папка существует и доступна на запись, места достаточно, сессия жива
 ├─ уборка: удалить оставшиеся *.part в _incoming и в папках месяцев периода
 ├─ проход 1, подсчёт: список из iCloud → для каждого ассета план → сводка
 │    (сколько в периоде, сколько уже есть, сколько качать и гигабайт)
 ├─ проверка, что всё поместится на диск
 ├─ проход 2, загрузка: список ещё раз → ассеты раздаются потокам
 │    └─ на каждый файл: .part → проверка размера → переименование → дата файла
 │       └─ для фото: JPG-копия в Compact в отдельном пуле
 └─ итог: отчёт, пометка задания завершённым или остановленным
```

Список запрашивается дважды, потому что ссылки на скачивание живут ограниченное время: на втором проходе файл качается сразу после получения его страницы.

### План для одного ассета

Одна и та же функция работает в обоих проходах. Она не обращается к сети, только к БД и диску.

1. **Фильтр.** Отбрасываются скрытые, удалённые, не подходящие по типу. Определяется набор файлов: оригинал, плюс видеочасть Live Photo и отредактированная версия, если это включено в настройках.
2. **Время съёмки** (подробнее ниже). Результат: месяц папки и вердикт «в периоде», «вне периода» или «неизвестно без файла».
3. **Имя и путь.** Если ассет уже есть в БД, берётся его закреплённый путь. Если нет, путь назначается и записывается в БД: при занятом имени добавляется суффикс из ID.
4. **Сверка с диском.** Для каждого файла:

| На диске | В БД | Действие |
| --- | --- | --- |
| есть, размер совпадает | любое | считается скачанным, в БД ставится «готов» |
| есть, размер другой | любое | конфликт: файл не трогаем, не качаем, пишем в отчёт |
| нет | «готов» | качаем заново; при настройке «не восстанавливать удалённые вручную» пропускаем |
| нет | нет или не «готов» | качаем |

Диск считается источником правды. БД только ускоряет работу и хранит закреплённые имена, поэтому её потеря не приводит к повторной загрузке.

### Время съёмки

Нужно «время на часах телефона в месте съёмки»: по нему выбирается папка месяца и решается, попадает ли снимок в период. Источники по порядку:

1. Смещение часового пояса, которое iCloud хранит вместе с ассетом. Время = момент съёмки UTC + смещение.
2. Время, прочитанное из файла раньше и сохранённое в БД.
3. Если пояса нет, но снимок дальше 14 часов от границы месяца и границ периода, то при любом поясе месяц и вердикт те же. Файл не нужен.
4. Иначе нужен сам файл. Сначала программа ищет его на диске (вдруг уже скачан). Если нет, скачивает в `_incoming`, читает EXIF `DateTimeOriginal` у фото или `com.apple.quicktime.creationdate` у видео, сохраняет результат в БД и переносит файл в нужный месяц. Если в файле даты нет, момент UTC переводится в часовой пояс компьютера.

Число 14 — максимальное отклонение часового пояса от UTC. С тем же запасом делается предварительный отбор по дате в iCloud.

### Загрузка одного файла

1. Клиент пишет в `<имя>.part` рядом с местом назначения.
2. Размер сравнивается с размером из iCloud.
3. Файл переименовывается в настоящее имя. Переименование отказывает, если имя уже занято.
4. Дата изменения файла ставится равной моменту съёмки.
5. В БД ставится статус «готов».

Обрыв на любом шаге оставляет только `.part`, который будет убран при следующем запуске. Под настоящим именем неполный файл появиться не может.

**Повторы.** Сетевая ошибка, 429 или 5xx, несовпадение размера: до 5 попыток с паузами 1, 2, 4, 8 секунд. Остальные ошибки без повторов.

**Устаревшая ссылка.** Ссылки на скачивание iCloud выдаёт вместе со списком файлов, и живут они ограниченное время. Если задание надолго зависло, сервер отвечает на такую ссылку 410. Повторять по ней бесполезно, поэтому файл откладывается, а после основного прохода движок запрашивает список периода заново и докачивает отложенное по свежим ссылкам; таких дополнительных проходов не больше двух. Уже скачанные файлы при этом не трогаются и в счётчики второй раз не попадают.

Не скачавшийся файл попадает в отчёт, задание идёт дальше; при следующем запуске он скачивается.

**Остановка задания целиком.** Истёкшая сессия, свободного места меньше порога, ошибка при получении списка, кнопка «Остановить». Уже начатые `.part` убираются, задание помечается остановленным и предлагается к продолжению.

### Параллельность

- Главный поток задания читает список из iCloud и раздаёт ассеты пулу загрузки (1–8 потоков, по умолчанию 3). В работе одновременно не больше `2 × потоков` ассетов, поэтому память не зависит от размера медиатеки.
- Один поток обрабатывает все файлы одного ассета подряд: так фото и его видеочасть получают согласованные имена.
- Начало каждого запроса к iCloud защищено общей блокировкой (библиотека пишет файлы сессии после каждого запроса). Тела файлов передаются параллельно.
- JPG-копии делает отдельный пул, по умолчанию половина ядер процессора. Он не занимает потоки загрузки.
- Пауза останавливает потоки между кусками данных. Остановка прерывает загрузки в процессе.

### Compact

Копия делается из локального оригинала после того, как он прошёл проверку размера, или если оригинал уже лежит, а копии нет. Сеть для этого не нужна.

Шаги: открыть (HEIC через pillow-heif) → повернуть пиксели по EXIF Orientation → залить прозрачность белым → перевести цвет в sRGB → уменьшить до выбранной длинной стороны, не увеличивая → сохранить JPG с датой съёмки, моделью камеры и GPS, Orientation = 1 → записать через `.part` и переименовать → поставить дату файла.

Копии получают фото HEIC, HEIF, JPG, PNG и их отредактированные версии. Видео, видеочасти Live Photo и RAW в Compact не попадают. Неудачная конвертация оставляет оригинал на месте, попадает в отчёт и повторяется при следующем запуске. Статус копии хранится в БД отдельно от статуса загрузки.

## База состояния

SQLite, один файл на аккаунт.

| Таблица | Содержимое |
| --- | --- |
| `files` | по строке на каждый файл: ассет, вид версии, относительный путь, размер, статус загрузки, путь и статус JPG-копии |
| `captures` | время съёмки, прочитанное из файлов |
| `jobs` | задания: период, статус, сколько всего и сколько готово |
| `meta` | версия схемы |

Путь уникален без учёта регистра, как в Windows: два ассета не могут получить одно имя. Повреждённый файл БД переименовывается в сторону и создаётся новый.

## События для интерфейса

Движок вызывает один callback `on_event(имя, **данные)` из своих потоков:

| Событие | Данные |
| --- | --- |
| `status` | `state`: `counting`, `downloading`, `paused`, `idle`, `error` |
| `plan` | объект `Plan` со сводкой перед загрузкой |
| `file` | `path`, `result`: `started`, `downloaded`, `present`, `error`, `conflict` |
| `bytes` | `count`: сколько байт только что записано |
| `report` | объект `Report` с итогом |

`Controller` превращает их в сигналы Qt. Ошибка внутри обработчика события задание не ломает.

## Интерфейс

```
ui/
  app.py           запуск, защита от второй копии, перехват необработанных ошибок
  controller.py    Controller: аккаунты, вход, сессия, запуск задания; без виджетов
  main_window.py   главное окно и значок в трее
  theme.py         цвета, шрифт и таблица стилей, светлая и тёмная тема
  login_dialog.py  Apple ID и пароль, затем код 2FA или SMS
  dialogs.py       аккаунты, настройки, журнал, список ошибок
  icons.py         значки, нарисованные кодом
```

### Controller

Единственная точка, через которую окна делают что-либо. Он хранит конфиг, клиентов iCloud по аккаунтам и текущее задание.

- **Фоновые операции.** Вход, проверка сессии, загрузка списка альбомов и само задание запускаются в отдельных потоках. Результат возвращается сигналом в поток интерфейса, поэтому окно не замирает ни при каком состоянии сети.
- **Вход.** `begin_login` → клиент отвечает «готово», «нужен код» или «ошибка» → диалог показывает нужную страницу. При успехе пароль уходит в Credential Manager, аккаунт записывается в конфиг.
- **Задание.** `start_job(period)` создаёт движок с настройками активного аккаунта и запускает его в потоке. События движка приходят из его рабочих потоков: счётчики байт и файлов складываются в `JobProgress` под блокировкой, остальное (состояние, сводка, ошибки по файлам, итог) уходит сигналами.
- **Запреты.** Пока идёт задание, нельзя переключить аккаунт, выйти из активного аккаунта и удалить его. Задание нельзя запустить без аккаунта, без выбранной папки и без действующей сессии; причина показывается рядом с кнопкой.

### Главное окно

Сверху вниз: выбор аккаунта и состояние сессии, блок задания (даты через календарь, «Весь период», быстрые варианты, кнопки «Запустить», «Пауза», «Остановить»), ход работы (состояние, сводка подсчёта, полоса, файлы, объём, скорость, оставшееся время, текущий файл), итог последнего запуска с кнопками «Показать ошибки» и «Открыть папку». Картинки окон лежат в `docs/screens`.

Окно само ничего не считает: раз в полсекунды оно читает счётчики у контроллера и обновляет надписи, остальное меняется по сигналам.

При входе в действующую сессию окно один раз проверяет, нет ли у аккаунта незавершённого задания, и предлагает продолжить.

### Трей и уведомления

Значок меняет цвет по состоянию: ожидание, загрузка, ошибка. Меню: «Открыть», «Пауза» или «Продолжить», «Остановить», «Выход». Крестик окна прячет его, программа продолжает работать в трее. Уведомления Windows: задание завершено (с итогом), задание остановлено, ошибка, нужен повторный вход. Щелчок по уведомлению о входе открывает диалог входа.

### Одна копия

Вторая запущенная копия находит первую по локальному сокету, просит её показать окно и завершается.

## Сборка и установка

```
src/ipd_app/locales/      переводы интерфейса: en, es, pt_br, zh_cn, ja (русский — в strings.py)
build.ps1                 одна команда: тесты → exe → самопроверка → аудит → установщик
packaging/
  launcher.py             точка входа собранной программы
  make_assets.py          значок и ресурс версии из исходников
  app.spec                описание сборки PyInstaller
  audit_bundle.py         поиск личных данных и секретов в собранной папке
  installer.iss           сценарий Inno Setup
  icon.ico
```

Как получается установщик:

1. `make_assets.py` рисует `icon.ico` и пишет ресурс версии из `ipd_app.__version__`.
2. PyInstaller собирает папку `dist\iCloudPhotoDownloader\` с `iCloudPhotoDownloader.exe` и всем, что ему нужно, включая Python. Модули `icloudpd` с кодом удаления из iCloud в сборку не попадают.
3. Собранный exe запускается с командой `selfcheck` и проверяет сам себя без сети: библиотека iCloud, сертификаты, Credential Manager, HEIC и JPG-копии, SQLite, задание на выдуманной медиатеке, Qt. При сбое сборка останавливается.
4. `audit_bundle.py` проверяет собранную папку, включая модули внутри exe: в ней не должно быть Apple ID, имени пользователя, путей, файлов сессии и настроек того, кто собирает. При находке сборка останавливается.
5. Inno Setup упаковывает эту папку, и только её, в `dist\iCloudPhotoDownloader-Setup-<версия>.exe`.

Установщик ставит программу в `%LOCALAPPDATA%\Programs\iCloudPhotoDownloader` без прав администратора и создаёт ярлык в меню «Пуск». Запуск exe без аргументов открывает окно; те же команды, что у `python -m ipd_app`, доступны и у exe.

Данные пользователя лежат отдельно от программы (таблица «Где что хранится»), поэтому обновление поверх старой версии их не затрагивает, а удаление программы спрашивает, убирать ли их.

## Безопасность

- Пароль хранится только в Windows Credential Manager. В конфиг, БД и логи он не попадает.
- Файлы сессии содержат токены входа в открытом виде. Так устроена библиотека; они лежат в профиле пользователя.
- Логи проходят через фильтр, который убирает пароли, коды 2FA, токены, cookies и параметры подписанных ссылок, а Apple ID маскирует.

## Что проверено и что нет

Проверено тестами без сети (223 теста): раскладка по месяцам в разных часовых поясах, границы периода, имена и конфликты, повторный запуск без загрузок, обрыв и докачка, уборка `.part`, восстановление после потери БД, фильтры, Compact, отсутствие секретов в логах, отсутствие вызовов удаления в адаптере. Для интерфейса: вход с 2FA и SMS, запуск, пауза и остановка задания из окна и из меню трея, запреты во время задания, сворачивание по крестику, настройки, удаление аккаунта, вторая копия. Командная строка и окно прогнаны целиком на сгенерированной медиатеке.

Проверено на реальном аккаунте (около 38 тысяч ассетов): вход и сохранение сессии, подсчёт и загрузка 320 файлов на 1,4 ГБ из командной строки и из окна, Live Photos, видео, часовой пояс съёмки, совпадение размеров, повторный запуск без загрузок. Собранный exe проходит самопроверку и видит тот же аккаунт. Первая проверка нашла ошибку в порядке списка, она исправлена (`DECISIONS.md`, D35–D38).

Не проверено:

- страница кода 2FA и SMS на настоящем сервере (при входе код не запрашивался);
- ADP, выключенный веб-доступ, истечение сессии, обрыв сети на настоящем сервере;
- задание на десятки гигабайт;
- отредактированные версии видео (`DECISIONS.md`, D38);
- значок в трее и уведомления Windows, масштаб экрана и тёмная тема (`CRITICAL_DECISIONS.md`, К15);
- установка на чистую Windows 11 без Python и удаление с ответом «Да» на вопрос о настройках (`CRITICAL_DECISIONS.md`, К18). Пробная установка и удаление на компьютере разработки прошли.
