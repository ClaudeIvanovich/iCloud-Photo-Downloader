# Решения и выводы

Формат: что решили, почему, что ещё не проверено. Статус «прочитано в коде» означает, что вывод сделан по исходникам `icloudpd` 1.33.0; «проверено на аккаунте» появится после запуска `scripts/stage0_probe.py` на реальном Apple ID.

## Этап 0. Проверка технологии (15.11.2026)

### D1. Библиотека iCloud: `pyicloud_ipd` из `icloudpd` 1.33.0

Берём её, форк `pyicloud` не нужен.

- Версия 1.33.0 вышла 04.11.2026, проект живой: в коде есть правки под изменения входа Apple 2026 года (push-запрос кода, новое место списка телефонов).
- `pyicloud_ipd` работает как обычная библиотека. Интерактивные `input()` и `sys.exit()` есть только в `icloudpd.authentication` и `icloudpd.base`, а их мы не импортируем.
- Из пакета `icloudpd` библиотека тянет один модуль, `icloudpd.paths` (чистка имён файлов). Код удаления из iCloud (`delete_photo`, `autodelete`) лежит в `icloudpd.base` и `icloudpd.autodelete` и при импорте `pyicloud_ipd` не загружается. В `pyicloud_ipd` запросов на изменение медиатеки нет.

Соответствие интерфейсу `ICloudClient` из раздела 5:

| Метод | Чем закрывается |
| --- | --- |
| `login` | Конструктор `PyiCloudService(domain, apple_id, password_provider, cookie_directory=...)`. Он сразу выполняет вход. Пароль запрашивается через callback, и только если сохранённая сессия не годится |
| нужен ли 2FA | свойства `requires_2fa`, `requires_2sa` |
| `submit_2fa_code` | `validate_2fa_code(code)`; перед этим `trigger_push_notification()`, иначе код на устройства не приходит |
| `request_sms_code` | `get_trusted_phone_numbers()`, `send_2fa_code_sms(id)`, `validate_2fa_code_sms(id, code)` |
| `is_session_valid` | Отдельного метода нет. Конструктор с callback, который возвращает `None`, бросает `PyiCloudFailedLoginException`, если сессия истекла |
| `list_albums` | `icloud.photos.albums` (словарь путь → альбом, с вложенными папками) |
| `iter_assets` | итерация по `icloud.photos.all` или альбому, генератор по страницам |
| `download` | `asset.versions[AssetVersionSize.ORIGINAL]` даёт `size`, `url`, `checksum`; `asset.download(session, url, start)` отдаёт поток с заголовком `Range`, то есть докачка возможна |

### D2. Установка: wheel `py3-none-any` по прямой ссылке

На Windows `pip install icloudpd` ставит wheel `win_amd64`. В нём лежит только готовый `icloudpd.exe` на 41 МБ, пакета `pyicloud_ipd` там нет. Исходного архива (sdist) на PyPI тоже нет. Поэтому в `requirements.txt` записана прямая ссылка на чистый Python-wheel с контрольной суммой SHA-256. Проверено установкой в `.venv`: `import pyicloud_ipd` работает.

Следствия:

- При обновлении версии ссылку и хеш надо менять вручную (взять из `https://pypi.org/pypi/icloudpd/<версия>/json`).
- `icloudpd` жёстко закрепляет свои зависимости (`requests==2.34.2`, `urllib3==2.8.0`, `keyring==25.7.0` и другие). Наши зависимости должны с ними совпадать. `keyring` той же версии используем и для паролей.
- Вместе с библиотекой приезжают `Flask`, `waitress`, `tqdm`, `fido2`, которые нам не нужны. В PyInstaller их стоит исключить (этап 3).

### D3. Сессия

Библиотека пишет в `cookie_directory` два файла, имя составлено из букв и цифр Apple ID: `<имя>` (cookies в формате LWP) и `<имя>.session` (JSON с токенами). Файлы перезаписываются после каждого HTTP-запроса. Задаём `cookie_directory = %APPDATA%\iCloudPhotoDownloader\sessions\<account_id>\`, где `account_id` — первые 16 символов SHA-256 от Apple ID в нижнем регистре. Так требование 6.1 выполняется, а адрес почты не попадает в имя папки (в имя файла внутри неё попадает, это делает библиотека).

Оба файла содержат токены входа в открытом виде. Требование про Credential Manager относится к паролю, но стоит знать: кто прочитал эти файлы, тот получил доступ к аккаунту до истечения сессии.

### D4. Порядок перечисления и период дат

Раздел 6.7 предполагал, что «Все фото» отдаются в порядке добавления. В 1.33.0 это не так: `photos.all` использует список `CPLAssetAndMasterByAssetDateWithoutHiddenOrDeleted`, то есть порядок по дате съёмки, без скрытых и удалённых. Направление в библиотеке зашито одно, от старых к новым.

Решение для этапа 1: перебирать по дате съёмки и прекращать перебор, когда `assetDate` ушла за конец периода плюс запас 14 часов.

Чего нет: фильтра по дате на стороне сервера. Чтобы не листать всю медиатеку до начала периода, есть два варианта.

1. Начинать с нуля и пропускать всё до начала периода. Просто, но для периода «прошлый месяц» на 50 000 файлов это около 250 лишних запросов (страница — 200 записей).
2. Найти начало двоичным поиском по `album.offset` (позиция в списке, атрибут публичный). Около 16 запросов на 50 000 файлов.

Предлагаю вариант 2 с откатом на вариант 1, если порядок окажется нестрогим. Проба использует тот же приём (`offset = всего − 20`), так что работоспособность видна уже на этапе 0.

Количество файлов (`len(album)`) приходит отдельным запросом, без перебора.

### D5. Часовой пояс съёмки

Библиотека запрашивает у iCloud поле `timeZoneOffset` для каждого ассета, но наружу его не отдаёт. Значение доступно через `asset._asset_record["fields"]["timeZoneOffset"]["value"]`. Это обращение к приватному атрибуту; оно останется в одном месте, в адаптере, и будет покрыто тестом на форму записи.

Не проверено на аккаунте: что поле заполнено у реальных снимков и что единица — секунды к востоку от UTC. Проба печатает сырое значение и вычисленное «время на телефоне» для 20 снимков. Нужно сравнить 2–3 строки с тем, что показывает приложение «Фото».

Если поле заполнено, первый источник из 6.3 работает без скачивания файла, и папка `_incoming` понадобится только для ассетов без смещения.

### D6. Требования раздела 3 частично устарели

- **ADP.** В 1.33.0 есть `request_pcs_consent()`: при включённой Advanced Data Protection библиотека запрашивает подтверждение веб-доступа на устройстве Apple, как это делает icloud.com. «Доступ к данным iCloud через веб» при этом всё равно должен быть включён. Варианты: (а) оставить как в требованиях, с ADP не работаем и показываем сообщение; (б) поддержать ADP через подтверждение на устройстве. Вариант (б) добавляет состояние «ждём подтверждения на телефоне» в диалог входа. Нужно решение владельца. В пробе это флаг `--adp`.
- **Ключи FIDO.** Библиотека их поддерживает (`confirm_security_key`, зависимость `fido2`). Требование «не поддерживается» можно оставить: это отдельный сценарий в интерфейсе.

Как отличить ADP от выключенного веб-доступа по ответу сервера без вызова `request_pcs_consent`, по коду не видно. Проба печатает флаги `iCDPEnabled`, `isWebAccessAllowed`, `pcsEnabled`, если они есть в ответе входа. Надёжное распознавание уточним на этапе 1.

### D7. Версии файла

`asset.versions` — словарь: `AssetVersionSize.ORIGINAL` (оригинал), `ADJUSTED` (отредактированная, для 6.2 `_edited`), `LivePhotoVersionSize.ORIGINAL` (видеочасть Live Photo), плюс уменьшенные. У каждой версии есть `size` в байтах, его достаточно для сверки из 6.7.

Ссылки на скачивание приходят вместе со страницей списка и со временем протухают. При долгом задании ссылку нужно брать из свежей страницы, а не хранить в очереди часами. Срок жизни ссылки не проверен.

### D8. Общие альбомы и общая медиатека

`photos.albums` для личной медиатеки возвращает пользовательские альбомы и «умные» папки (Favorites, Videos, Hidden, Recently Deleted и другие). Общая медиатека доступна только через отдельное свойство `shared_libraries`, которое мы не вызываем. В списке альбомов адаптер должен скрыть `Hidden` и `Recently Deleted` (требование 6.2).

### D9. Новые зависимости

| Пакет | Зачем |
| --- | --- |
| `icloudpd` 1.33.0 | доступ к iCloud, см. D1 и D2 |
| `pytest` 8.4.2 (dev) | тесты, раздел 4 требований |

## Что осталось проверить на реальном аккаунте

Запуск: `.venv\Scripts\python.exe scripts\stage0_probe.py --apple-id <Apple ID>`

1. Вход с паролем и кодом 2FA проходит, печатается «[1] Вход выполнен».
2. Повторный запуск не спрашивает ни пароль, ни код.
3. В таблице 20 последних снимков, порядок по дате съёмки, столбец `tz, raw` заполнен, «время на телефоне» совпадает с приложением «Фото».
4. Три файла лежат в `_stage0_downloads` и открываются.

Если пункт 1 не проходит, дальнейшие этапы не начинаем (правило этапа 0).

Обновление от 15.11.2026: первый запуск пробы вернул «неверный Apple ID или пароль» (−20283). Ввод пароля в консоли исправлен, повторной проверки пока не было. Владелец решил начать этап 1 без неё, см. `CRITICAL_DECISIONS.md`, К1.

## Этап 1. Ядро (15.11.2026)

Решения, которые меняют поведение для пользователя или отступают от требований, вынесены в `CRITICAL_DECISIONS.md`. Здесь технические.

### D10. Интерфейс `ICloudClient` шире, чем в требованиях

К методам из раздела 5 добавлены два: `submit_sms_code(phone_id, code)` (код из SMS подтверждается другим запросом, чем код с устройства) и `count_assets(filter)` (быстрый счётчик для прогресса; для периода дат iCloud его не даёт, тогда возвращается `None`). Методов изменения или удаления нет.

### D11. Идентификатор ассета — запись CPLAsset, а не CPLMaster

У библиотеки `asset.id` — это ID мастер-записи. Несколько ассетов могут делить один мастер (функция «Дублировать» в «Фото»), и тогда ID совпадают. Адаптер берёт `recordName` записи ассета.

### D12. Отредактированная версия

Версия «edited» берётся, только если поле `resJPEGFull` (для видео `resVidFull`) есть в записи ассета. То же поле в мастер-записи считается служебным JPEG-представлением оригинала, а не правкой. На реальном аккаунте не проверено. Правки видео библиотека сама не отдаёт, адаптер читает поле напрямую.

### D13. Поиск начала периода

Реализован вариант 2 из D4: двоичный поиск по позиции в списке (около 16 запросов на 50 000 файлов), затем шаг назад на страницу (200 записей) на случай нестрогого порядка. Если поиск упал с любой ошибкой, перебор идёт с начала. Перебор прекращается после целой страницы ассетов позже конца периода.

При сетевой ошибке посреди списка перебор продолжается с того же места, до 4 повторов с растущей паузой.

### D14. Пароль после входа

Библиотека хранит функцию, возвращающую пароль, всё время жизни объекта и может тихо войти заново. После успешного входа адаптер подменяет её на пустую: пароль не остаётся в памяти, а истёкшая сессия даёт понятную ошибку «войдите заново».

### D15. Пароль в Credential Manager хранится под ID аккаунта

Имя записи — `iCloudPhotoDownloader` / первые 16 символов SHA-256 от Apple ID. Сам адрес в имени записи не светится.

### D16. Логи

Фильтр секретов висит на обработчиках корневого логгера и поэтому действует и на записи библиотек. Он вычищает: зарегистрированные пароли и коды 2FA (любое вхождение строки), значения полей `password`, `*token`, `scnt`, `cookie`, `securityCode` и подобных, шестизначные числа после слова `code`, параметры подписанных ссылок на скачивание, адреса почты (маска `al***@example.com`). Коды ошибок Apple вроде `-20283` остаются читаемыми. Уровень DEBUG для `pyicloud_ipd` не включается никогда: на нём библиотека пишет тела запросов.

### D17. Имена файлов

Недопустимые символы `< > : " / \ | ? *` и управляющие заменяются на `_`. Точки и пробелы в конце убираются. Зарезервированные имена (`CON`, `NUL`, `COM1`…) получают `_` в начале. Имя длиннее 180 символов обрезается с сохранением расширения. Пути длиннее 240 символов открываются через префикс `\\?\`, включая сетевые (`\\?\UNC\`).

### D18. Публикация файла

Временный файл переименовывается через `os.rename`, а не `os.replace`: на Windows `rename` отказывает, если цель существует, и это вторая страховка от перезаписи. При `PermissionError` (антивирус, индексатор) до 5 повторов.

### D19. Задания в БД

В БД хранится не больше одного незавершённого задания. Запуск задания на тот же период продолжает его, запуск на другой период закрывает старое. Прогресс для вопроса «Продолжить?» — число уже лежащих на диске и скачанных файлов.

### D20. Оценка места под Compact

На файл берётся меньшее из двух: типичный размер JPG для выбранной длинной стороны (0,5 МБ для 1600, 0,8 МБ для 2048, 2,5 МБ для 4096, 3,5 МБ без уменьшения, с поправкой на качество) и размер оригинала.

### D21. Память

Список ассетов не хранится. На время прохода хранится только множество ID (чтобы ассет из двух альбомов не обработать дважды): около 100 байт на ассет, 5 МБ на 50 000 файлов. Одновременно в работе не больше `2 × параллельность` ассетов.

### D22. Конфигурация

`config.json` хранит версию схемы. При загрузке применяется цепочка миграций (сейчас одна: файл без версии → версия 1). Неизвестные ключи игнорируются, чтобы откат на старую версию программы не ломал запуск. Запись атомарная: временный файл и замена.

### D23. Отладочный CLI и режим `--fake`

`python -m ipd_app sync --fake N --root <папка>` запускает движок на сгенерированной медиатеке из N ассетов с настоящими JPEG, без iCloud. Нужен для разработки GUI и ручной проверки. БД состояния для этого режима кладётся рядом с папкой (`<папка>.state.sqlite`), чтобы не смешиваться с настоящими аккаунтами.

### D24. Новые зависимости этапа 1

| Пакет | Зачем |
| --- | --- |
| `pillow` 13.0.0 | JPG-копии и чтение EXIF, раздел 4 требований |
| `pillow-heif` 1.8.1 | чтение HEIC; несёт libheif 1.23.6 (LGPL) отдельной DLL |
| `keyring` 25.7.0 | пароль в Credential Manager; версия совпадает с закреплённой в `icloudpd` |
| `ruff` (dev) | проверка на неиспользуемые имена и синтаксис |

Для чтения даты из видео новой зависимости нет: разбор атомов QuickTime написан вручную (около 70 строк в `capture.py`).

### Что не проверено на реальном аккаунте (сводка)

1. Вход, 2FA, сохранение сессии (К1).
2. Заполнено ли `timeZoneOffset` и в секундах ли оно (D5).
3. Поля отредактированных версий (D12).
4. Распознавание ADP и выключенного веб-доступа (К2).
5. Срок жизни ссылок на скачивание и работа блокировки запросов при параллельной загрузке (D7, К10).
6. Совпадает ли размер файла из метаданных с размером скачанного. На этом сравнении построена вся сверка; если для каких-то типов они расходятся, такие файлы будут уходить в ошибки «размер не совпал».

## Этап 2. Окна и трей (15.11.2026)

### D25. PySide6-Essentials вместо полного PySide6

Нужны только QtCore, QtGui, QtWidgets и QtNetwork. Пакет Essentials содержит их и заметно меньше полного (в нём нет WebEngine, 3D, Quick и прочего), что уменьшит установщик. Версия 6.12.0, лицензия LGPL-3.0.

### D26. Сетевые операции вне потока интерфейса

Вход, проверка сессии, список альбомов и задание выполняются в отдельных потоках (`Task`, наследник `QThread`). Результат возвращается одним сигналом в слот контроллера через очередь событий, поэтому обработчики всегда работают в потоке интерфейса.

Найдено на тестах и исправлено: обычная функция, подключённая к сигналу, в PySide выполняется в потоке, который сигнал испустил. Из-за этого обработчики результатов запускались в рабочем потоке, и процесс падал. Теперь результаты идут только через слот объекта `Controller`.

### D27. Прогресс опрашивается таймером

Счётчики байт и файлов пишутся потоками загрузки под блокировкой, окно читает их раз в 500 мс. Сигнал на каждый кусок данных (до нескольких тысяч в секунду при восьми загрузках) забивал бы очередь событий. Скорость считается по окну в 5 секунд.

### D28. «Пауза» и «Стоп», нажатые сразу после запуска

Найдено на тестах: движок сбрасывал флаги управления в начале задания, и нажатие в первые миллисекунды, пока поток задания стартует, терялось. Теперь флаги сбрасываются в конце задания.

### D29. Одна копия программы

Первая копия открывает локальный сокет с именем `iCloudPhotoDownloader-<хеш от имени пользователя Windows>`. Вторая подключается к нему и завершается, первая по факту подключения показывает своё окно. Имя сокета, оставшееся после аварийного завершения, перед прослушиванием снимается.

### D30. Значки

Значок приложения и три значка трея (ожидание синий, загрузка зелёный, ошибка красный) рисуются кодом: скруглённый квадрат со стрелкой вниз. Чужих изображений нет. На этапе 3 из той же функции получится `icon.ico`.

### D31. Закрытие окна и выход

Крестик прячет окно, программа остаётся в трее и один раз сообщает об этом. Если трея в системе нет, крестик закрывает программу, с вопросом при идущем задании. «Выход» в меню трея при идущем задании спрашивает подтверждение, останавливает задание, ждёт потоки и завершает программу.

### D32. Журнал

Окно читает хвост `app.log` (до 2000 записей) и фильтрует по уровню. Многострочная запись, например ошибка с трассировкой, показывается целиком вместе со своей первой строкой. Автообновления нет, есть кнопка «Обновить».

## Проверка на реальном аккаунте (15.11.2026)

### D35. «Все фото» приходят от новых к старым

В D4 я написал, что список идёт от старых к новым: в запросе библиотеки стоит `direction: ASCENDING`. На реальном аккаунте позиция 0 оказалась самым новым снимком, последняя позиция самым старым. Из-за этого поиск начала периода уходил в конец медиатеки, и любое задание находило ноль файлов. Тесты этого поймать не могли: заглушка списка была построена по тому же неверному предположению.

Исправление: клиент больше не предполагает направление. Он читает даты на первой и последней позиции и по ним решает, как искать начало периода и когда прекращать перебор. Найденная стартовая позиция запоминается на 10 минут, потому что задание проходит по списку дважды. Добавлены тесты на оба направления.

Следствие для имён файлов (К4): чистое имя получает тот из одноимённых снимков, который встретился в списке первым, то есть более новый. На постоянство имён это не влияет.

### D37. Что осталось непроверенным

1. **Код 2FA.** При входе код не запрашивался (устройство уже было доверенным или сработала сохранённая сессия), поэтому страница кода и SMS на настоящем сервере не проверены.
2. **Live Photos.** Среди 14 скачанных HEIC не оказалось ни одной видеочасти `.MOV`. Либо это не Live Photos, либо видеочасть не распознаётся. Нужно проверить на заведомо «живом» снимке.
3. **Отредактированные версии (D12).** У пробного снимка поле `resJPEGFull` есть в записи ассета, но его размер равен размеру оригинала. Возможно, это поле есть у всех снимков, и тогда опция «скачивать отредактированную версию» будет создавать копии оригиналов. Опция по умолчанию выключена.
4. **ADP и выключенный веб-доступ**, истечение сессии через два месяца, обрыв сети посреди загрузки на настоящем сервере.
5. **Длительное задание** на десятки гигабайт: срок жизни ссылок и поведение Apple при большом объёме.

### D38. Вторая проверка: Live Photos, видео, правки (15.11.2026)

Задание из окна за два дня: 141 ассет, 219 файлов, 663 МБ, ошибок нет.

- **Live Photos работают** (закрывает пункт 2 из D37): у 78 фото из 134 есть видеочасть, все 78 `.MOV` скачаны рядом со своими фото.
- **Видео скачиваются**: iCloud отдал за период 7 видео (`.MOV`, от 2 до 26 МБ, 2–19 секунд), все 7 лежат на диске, размеры совпадают. В папке они стоят вперемешку с 78 видеочастями Live Photos и по имени от них не отличаются: так задано раскладкой из ТЗ (всё в `Full size`).
- **Правки фото** (уточняет пункт 3 из D37): поле `resJPEGFull` есть у 6 фото из 134, и у всех шести есть признак правки `adjustmentType`. Значит, поле появляется только у отредактированных снимков, и правило из D12 для фото верное.
- **Правки видео**: поле `resVidFull` и признак правки есть у 6 видео из 7. Столько правок подряд маловероятно; возможно, iPhone ставит этот признак автоматически (обрезка, стабилизация). Если включить опцию «скачивать отредактированную версию», почти у каждого видео появится второй файл `_edited`. Опция по умолчанию выключена, вопрос открыт.

## Этап 3. Сборка и установщик (15.11.2026)

### D39. Состав сборки

PyInstaller 6.22.3, режим «папка» (`dist\iCloudPhotoDownloader\`), без UPX: упакованные UPX файлы чаще вызывают ложные срабатывания антивирусов. Папка занимает около 158 МБ, основной объём дают Qt и кодеки HEIC.

Исключено из сборки: `flask`, `waitress`, `werkzeug`, `jinja2`, `tqdm` (веб-интерфейс и индикатор `icloudpd`), `keyrings.alt` (см. D41), `tkinter`, модули `icloudpd.base`, `icloudpd.cli`, `icloudpd.autodelete`, `icloudpd.server`. Последние четыре содержат код удаления из iCloud; в собранной программе его нет физически.

Добавлено явно: сертификаты `certifi`, база часовых поясов `tzdata`, метаданные `keyring` (без них он не находит хранилище Windows), библиотеки `pillow_heif`. libheif остаётся отдельной DLL, как требует LGPL.

### D40. Самопроверка сборки

У оконного exe нет консоли, поэтому «запустился и не упал» ничего не доказывает. Добавлена команда `selfcheck <файл отчёта>`. Она без сети и без обращения к аккаунтам проверяет восемь вещей: импорт библиотеки iCloud и наличие сертификатов, TLS, часовые пояса, доступ к Credential Manager, чтение HEIC и создание JPG-копии с профилем sRGB, SQLite, полный прогон задания на выдуманной медиатеке, запуск Qt и отрисовку значка. `build.ps1` запускает её на собранном exe и останавливает сборку при любом сбое.

### D41. Хранилище паролей задано явно

`keyring` по умолчанию сам выбирает хранилище из найденных. Вместе с `icloudpd` приезжает пакет `keyrings.alt`, в котором есть хранилища в обычном файле. Чтобы пароль никогда не оказался в файле, программа создаёт `WinVaultKeyring` (Credential Manager) напрямую, а `keyrings.alt` исключён из сборки. Пароль, сохранённый раньше через автоматический выбор, читается по-прежнему: он и тогда лежал в Credential Manager (проверено на вашей записи).

### D42. Версия

Единственный источник — `ipd_app.__version__`. `packaging/make_assets.py` делает из неё ресурс версии для exe, `build.ps1` передаёт её в Inno Setup параметром `/DAppVersion`, она же попадает в имя установщика.

### D43. Значок

`packaging/icon.ico` (7 размеров, от 16 до 256) создаётся из той же функции, что рисует значки трея. Файл лежит в репозитории, а при сборке создаётся заново.

### D44. Установщик

- Установка в `%LOCALAPPDATA%\Programs\iCloudPhotoDownloader`, права администратора не нужны (`PrivilegesRequired=lowest`).
- Ярлык в меню «Пуск», ярлык на рабочем столе по галочке (по умолчанию выключена).
- `AppId` постоянный: установка новой версии находит старую и ставится поверх. Настройки, сессии и БД лежат в профиле пользователя и при обновлении не затрагиваются.
- При обновлении поверх работающей программы установщик просит её закрыть.
- Деинсталляция удаляет программу и спрашивает, удалять ли настройки (по умолчанию «Нет»). При ответе «Да» сначала вызывается `iCloudPhotoDownloader.exe forget-credentials`, которая убирает пароли из Credential Manager и файлы сессий, затем удаляются папки программы в `%APPDATA%` и `%LOCALAPPDATA%`. Скачанные фото деинсталлятор не трогает и не знает, где они лежат.
- Язык мастера русский.

### D47. Аудит сборки и проверка установщика

`packaging/audit_bundle.py` разбирает архив Python внутри exe средствами PyInstaller и проверяет каждый модуль в распакованном виде. Проверено отдельно: строка, которая есть только в `ipd_app/selfcheck.py`, находится внутри архива и не находится в сырых байтах exe, то есть аудит действительно читает содержимое, а не сжатые данные.

Общедоступный набор корневых сертификатов `certifi\cacert.pem` разрешён явно. Правила для ключей и cookies требуют настоящего тела ключа или значения cookie: строки-маркеры в коде библиотек (`-----BEGIN PRIVATE KEY-----` в Qt, `#LWP-Cookies-` в `http.cookiejar`) под них не подпадают.

Сценарий установщика принимает папку-источник параметром `/DSourceDir`. Вопрос деинсталлятора о настройках в тихом режиме получает ответ «Нет».

`build.ps1` отказывается собирать, если запущена программа из `dist\`: она держит свои файлы, и PyInstaller падает с «Отказано в доступе».

Установщик 0.1.0: 41 МБ, после установки 158 МБ.

### D48. Публичная копия

`scripts/make_public_copy.py` отказывается работать при незакоммиченных изменениях и не перезаписывает папку, в которой уже есть `.git`. Правила замены заданы списком `REWRITES`; если правило перестало совпадать с текстом, скрипт останавливается, чтобы замена не пропала молча. Сам скрипт в публичную копию не входит.

Проверка `ruff` в GitHub Actions не включена: в проекте нет настроек `ruff`, и с правилами по умолчанию он выдаёт замечания по стилю.

### D49. Устройство переводов

`strings.py` остался списком всех текстов и хранит русские оригиналы. Переводы лежат в `locales/en.py`, `es.py`, `pt_br.py`, `zh_cn.py` и повторяют его имя в имя. `strings.set_language()` подменяет значения на месте, поэтому остальной код по-прежнему читает `strings.X` и `UI.X`. Сторонняя библиотека переводов (gettext, Qt Linguist) не понадобилась: текстов около 190, а формат «модуль Python» проверяется обычными тестами и не требует шага компиляции.

Следствие: текст нельзя читать во время импорта модуля, язык выбирается позже. Три таких места исправлены: тексты ошибок iCloud (теперь класс хранит имя текста и берёт сам текст при создании ошибки), значение по умолчанию у `SyncEngine.stop` и таблица названий состояний в главном окне.

Тесты: в каждом переводе есть все тексты, совпадают подстановки `{...}`, число переносов строк и длина кортежей, не осталось кириллицы; после переключения языка ни в одном окне нет русского текста (проверяются главное окно после задания и все диалоги). Последний тест и нашёл таблицу состояний.

Переводы стандартных кнопок Qt берутся из файлов `qtbase_*.qm`, которые PyInstaller уже кладёт в сборку. Для запуска с нужным языком без смены настроек есть `gui --lang <код>`.

Язык хранится в `config.json` в поле `language` (`auto` или код). Версия формата не менялась: у старого файла поля нет, и это читается как `auto`.

### D50. Тема оформления

Все цвета, шрифт и таблица стилей лежат в `ui/theme.py`. Окна цветов не задают: виджет получает свойство (`role` у подписей, `primary`, `chip`, `link` у кнопок, `card` у панелей), а как это выглядит, решает таблица стилей. Раньше цвета были вписаны в окна в пяти местах; в тёмной теме они бы не читались.

Основа — стиль Qt Fusion: он одинаков на всех версиях Windows и полностью подчиняется таблице стилей. Палитра Qt тоже выставляется, для того, до чего таблица не дотягивается (календарь, значки сообщений).

Кнопки периодов стали отмечаемыми; «Весь период» из флажка превратился в такую же кнопку с теми же методами `setChecked`/`isChecked`, поэтому остальной код и тесты не менялись.

Отступ текста в числовых полях настроек задан в коде: таблица стилей Qt не достаёт до внутреннего поля ввода.

Тесты: кнопки задания показываются и прячутся по состоянию; подсвечивается ярлык текущего периода; тема собирается для обеих схем, наборы цветов совпадают по составу.
