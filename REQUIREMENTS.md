# iCloud Photo Downloader для Windows — требования


Документ написан как техническое задание для Claude Code. Его можно положить в корень репозитория как `REQUIREMENTS.md` (экспорт в Markdown) и попросить Claude Code работать по нему поэтапно.

## 1. Цель

Десктопное приложение для Windows, которое подключается к iCloud Photos под Apple ID пользователя, выбирает фото и видео за заданный период и скачивает их в выбранную пользователем папку (локальную или сетевую), раскладывая по папкам `ГГГГ\ММ Month` по дате съёмки. Внутри каждого месяца лежат оригиналы (папка Full size) и облегчённые JPG-копии фото (папка Compact). В первой версии (MVP) загрузка запускается вручную как задание на период дат. Пока задание идёт, приложение может работать из трея. Ставится через обычный установщик.

Приложение работает только на чтение: ничего не удаляет и не меняет ни в iCloud, ни в уже скачанных локальных файлах.

## 2. Принятые решения

| Вопрос | Решение |
| --- | --- |
| Платформа | Windows 10/11 x64. Ядро пишется кроссплатформенным, но собирается и тестируется только под Windows |
| Аккаунты | Можно сохранить несколько Apple ID и переключаться между ними. Активен и синхронизируется один аккаунт за раз |
| Режим | Только копирование. Удалений нет нигде |
| Интерфейс | Окно с настройками и прогрессом + значок в трее, загрузка запускается вручную как задание на период. Мониторинг по расписанию отложен (раздел 12) |
| Язык | Интерфейс на русском (строки вынесены для будущей локализации), код, комментарии и логи на английском |
| Структура папок | `<папка, выбранная пользователем>\ГГГГ\ММ Month\`, внутри месяца две папки: `Full size` (оригиналы) и `Compact` (JPG-копии фото). Например `2023\03 March\Compact` |

## 3. Ограничения со стороны Apple (важно прочитать до начала работы)

У Apple нет публичного API для iCloud Photos. Все существующие инструменты имитируют веб-клиент icloud.com. Отсюда следуют жёсткие условия:

- **Advanced Data Protection (ADP) должна быть выключена.** С ADP веб-доступ к фото отключён, и программа работать не сможет.
- В настройках iCloud на iPhone должна быть включена опция «Доступ к данным iCloud через веб» (Access iCloud Data on the Web).
- Вход через аппаратные ключи безопасности (FIDO) не поддерживается.
- Apple периодически меняет протокол входа и 2FA. Поэтому слой работы с iCloud должен быть изолирован (см. раздел 5), а зависимость закреплена на конкретной версии.
- Сессия после 2FA живёт ограниченное время (обычно около двух месяцев), после чего нужен повторный вход с кодом.

Приложение должно распознавать эти ситуации и показывать понятное сообщение на русском, а не трейсбек: «Включена Advanced Data Protection», «Веб-доступ к iCloud выключен», «Сессия истекла, войдите заново».

## 4. Технологический стек

- **Python 3.12**.
- **Доступ к iCloud:** библиотека `pyicloud_ipd` из пакета `icloudpd` (проект icloud-photos-downloader, MIT, активно поддерживается и чинится под изменения Apple). Версию закрепить в `requirements.txt`. Если на этапе 0 выяснится, что использовать её как библиотеку неудобно, допустимая альтернатива — форк `pyicloud`. Решение и причины записать в `docs/DECISIONS.md`.
- **GUI и трей:** PySide6 (Qt), `QSystemTrayIcon`.
- **Хранение паролей:** `keyring` (Windows Credential Manager). Пароль никогда не пишется в конфиг, логи или на диск в открытом виде.
- **Состояние синхронизации:** SQLite (стандартный `sqlite3`).
- **Обработка изображений (Compact):** Pillow + `pillow-heif` для чтения HEIC. `pillow-heif` использует libheif (LGPL): проверить, что PyInstaller подключает её как динамическую библиотеку, и перечислить лицензии в README.
- **HTTP:** то, что использует выбранная библиотека iCloud (requests), с повторами и backoff.
- **Сборка:** PyInstaller в режиме `--onedir` (быстрее стартует и реже даёт ложные срабатывания антивируса, чем onefile) + установщик **Inno Setup**.
- **Тесты:** pytest.

## 5. Архитектура

Три слоя, связанные через интерфейсы:

1. **`icloud_adapter`** — единственное место, где есть код, знающий об iCloud. Интерфейс `ICloudClient`:
   - `login(apple_id, password) -> LoginResult` (успех / нужен 2FA / ошибка с типом)
   - `submit_2fa_code(code)`, `request_sms_code(...)`
   - `is_session_valid()`
   - `list_albums()`
   - `iter_assets(filter) -> Iterator[Asset]`
   - `download(asset, version, dest_path, progress_cb)`
   - **Методов удаления или изменения нет вообще.** Код не должен вызывать delete-методы библиотеки ни при каких условиях. Добавить тест, который проверяет это (например, grep по исходникам адаптера на `delete`).
   - Плюс `FakeICloudClient` для тестов и разработки GUI без реального аккаунта.
2. **`sync_engine`** — фильтрация, построение путей, очередь загрузок, параллельность, возобновление, работа с БД состояния. Не знает про Qt.
3. **`ui`** — окна, трей, уведомления. Движок запускается в отдельном потоке (`QThread` или worker), UI общается с ним через сигналы. UI никогда не блокируется сетевыми операциями.

Структура репозитория (ориентир):

## 6. Функциональные требования

### 6.1 Аккаунты и вход

- Добавить аккаунт: Apple ID + пароль → при необходимости диалог ввода 6-значного кода 2FA (с кнопкой «Прислать SMS», если библиотека это поддерживает).
- Список сохранённых аккаунтов, переключение активного, удаление аккаунта из приложения (удаляет только сохранённые данные входа и сессию, скачанные файлы не трогает).
- Для каждого аккаунта пользователь сам выбирает корневую папку (см. 6.3). В интерфейсе аккаунт показывается по Apple ID, папки по нему не создаются.
- Файлы сессии/cookies хранятся отдельно для каждого аккаунта в `%APPDATA%\iCloudPhotoDownloader\sessions\<account_id>\`.
- При истечении сессии: синхронизация останавливается, в трее уведомление «Нужен повторный вход», по клику открывается диалог 2FA.
- Переключение аккаунта во время синхронизации запрещено (сначала остановить).

### 6.2 Выбор файлов (фильтры)

Настраиваются для каждого аккаунта отдельно:

- Источник: личная медиатека аккаунта («Все фото») или выбранные альбомы из неё. Общие альбомы (Shared Albums) и общая медиатека (Shared Library) не скачиваются и в списке альбомов не показываются. Фото, которые владелец аккаунта сам добавил в общий альбом, и так есть в его медиатеке, а у второго аккаунта будет свой архив.
- Тип: фото, видео или оба.
- Период съёмки «с» / «по» задаётся при запуске задания, подробнее в 6.7.
- Live Photos: скачивать ли видеочасть (по умолчанию да, кладётся рядом с фото с тем же базовым именем).
- Версия: оригинал (по умолчанию). Опция «также скачивать отредактированную версию» с суффиксом `_edited`.
- Не скачивать: «Скрытые» и «Недавно удалённые» (всегда исключены).

### 6.3 Раскладка по папкам и именование

- Корневую папку пользователь выбирает сам, отдельно для каждого аккаунта. Внутри неё программа создаёт только папки года и месяца, а внутри месяца две папки, `Full size` и `Compact` (состав описан в 6.3.1): `<корневая папка>\<ГГГГ>\<ММ Month>\Full size\<имя файла>`. Например `D:\Photos\Georgy\2023\03 March\Full size\IMG_1234.HEIC` и `D:\Photos\Georgy\2023\03 March\Compact\IMG_1234.jpg`. Других подпапок программа не создаёт. При первом входе в аккаунт программа сразу просит выбрать папку; пока она не выбрана, задание запустить нельзя.
- Папка месяца называется двузначным номером месяца и английским названием с заглавной буквы через пробел: `01 January`, `02 February`, `03 March`, … `12 December`. Номер нужен, чтобы Проводник сортировал месяцы по календарю. Названия зашиты в коде и не зависят от языка Windows (не брать их из системной локали через `strftime`).
- Если два аккаунта указывают на одну и ту же корневую папку, предупредить пользователя: файлы обоих аккаунтов окажутся в одних и тех же папках месяцев.
- **Дата берётся из даты съёмки ассета в iCloud** (asset date, совпадает с EXIF). Если её нет — дата добавления в iCloud. Если нет и её — папка `Unknown date`.
- **Год и месяц определяются по времени съёмки, как оно записано в метаданных файла**, то есть по часам телефона в месте съёмки, независимо от часового пояса компьютера. Снимок, сделанный 31 декабря в 23:30 в Бангкоке, попадает в декабрь, снимок из Нью-Йорка в 01:00 1 января попадает в январь. Порядок источников: (1) часовой пояс съёмки из метаданных ассета в iCloud, если библиотека его отдаёт; (2) EXIF `DateTimeOriginal` + `OffsetTimeOriginal` из файла фото, для видео `com.apple.quicktime.creationdate`; (3) `DateTimeOriginal` без смещения берётся как есть; (4) только если ничего из этого нет, дата из iCloud в UTC переводится в часовой пояс Windows. Если время съёмки можно узнать только из самого файла, файл сначала скачивается во временную служебную папку `_incoming` в корневой папке и после чтения метаданных переносится на место; пустая `_incoming` удаляется в конце задания. Видеочасть Live Photo всегда ложится в ту же папку, что и фото. Покрыть тестами переходы через полночь, конец месяца и Новый год в разных часовых поясах.
- Имя файла — оригинальное из iCloud. При конфликте имён в одной папке (разные ассеты с одинаковым `IMG_0001.HEIC`) добавлять короткий суффикс из ID ассета: `IMG_0001_a1b2c3.HEIC`. Один и тот же ассет всегда получает одно и то же имя (детерминированно).
- Недопустимые для Windows символы в именах заменять; учитывать лимит длины пути (поддержка длинных путей через `\\?\` или проверка с понятной ошибкой).
- После загрузки выставить файлу дату изменения (mtime) равной дате съёмки. Содержимое файла не менять.

### 6.3.1 Папки Full size и Compact

Внутри каждой папки месяца программа создаёт две папки:

- **`Full size`**: всё, что скачано из iCloud, без изменений. Это фото (HEIC, JPG, PNG, DNG), видео (MOV, MP4), видеочасть Live Photos и отредактированные версии с суффиксом `_edited`.
- **`Compact`**: JPG-копии фотографий для быстрого просмотра и отправки. Они открываются на любом устройстве без дополнительных расширений. Видео и видеочасть Live Photos сюда не попадают.

Правила для Compact:

- JPG-копия создаётся для каждого фото в форматах HEIC, HEIF, JPG и PNG, включая отредактированные версии. Для DNG в MVP копия не делается, такой файл лежит только в Full size.
- Имя копии совпадает с именем оригинала, расширение `.jpg`: `IMG_1234.HEIC` → `IMG_1234.jpg`. Суффикс конфликта или `_edited` сохраняется. Если в Full size два оригинала с одним базовым именем и разными расширениями (`IMG_1234.HEIC` и `IMG_1234.PNG`), к имени копии добавляется исходное расширение: `IMG_1234_png.jpg`.
- Размер по длинной стороне настраивается: без уменьшения / 4096 / 2048 / 1600 px, по умолчанию 2048. Качество JPG от 60 до 95, по умолчанию 85. Маленькие фото не увеличиваются.
- Поворот по тегу EXIF Orientation применяется к пикселям, а в копии Orientation ставится 1. Иначе в программах, которые игнорируют тег, фото ляжет боком.
- Из EXIF в копию переносятся дата съёмки, модель камеры и GPS. Цветовой профиль конвертируется в sRGB, потому что iPhone снимает в Display P3. Прозрачность PNG заливается белым.
- Дата изменения файла копии равна дате съёмки, как у оригинала.
- Копия делается из уже скачанного локального оригинала, когда он прошёл проверку размера. Запись тоже через временный файл и атомарное переименование.
- Конвертация идёт в отдельном пуле процессов или потоков и не тормозит загрузку. Число параллельных конвертаций по умолчанию равно половине ядер процессора.
- Если конвертация не удалась, оригинал остаётся в Full size, ошибка попадает в отчёт, и при следующем запуске программа пробует снова.
- В БД статус Compact хранится отдельно от статуса загрузки.
- Compact можно выключить в настройках (по умолчанию включён). Тогда новые копии не создаются, а уже созданные не удаляются.
- Оценка нужного места перед запуском учитывает и Compact (приблизительно, по числу фото и выбранному размеру).

### 6.4 Синхронизация

- **Инкрементальность:** БД состояния (SQLite, на каждый аккаунт) хранит ID ассета, версию, итоговый путь, размер, статус, время загрузки. Уже скачанное не качается повторно. Если файл есть на диске с правильным размером, но его нет в БД (например после переустановки) — считать скачанным и записать в БД.
- **Надёжность:** загрузка во временный файл `*.part` в той же папке → проверка размера → атомарное переименование. Обрыв на середине не оставляет битых файлов под настоящим именем.
- **Возобновление:** после закрытия приложения или сбоя следующая синхронизация продолжает с места остановки: сверяет список файлов из iCloud с БД и с содержимым корневой папки и докачивает только недостающее (алгоритм в 6.7).
- **Параллельность:** 1–8 одновременных загрузок, по умолчанию 3.
- **Повторы:** при сетевых ошибках, 429/5xx — экспоненциальный backoff, до 5 попыток на файл. Файл, который так и не скачался, помечается как ошибка, синхронизация идёт дальше, в конце отчёт.
- **Свободное место:** перед стартом и во время работы проверять свободное место на целевом диске; остановиться с понятным сообщением, если меньше настраиваемого порога (по умолчанию 5 ГБ).
- **Целевая папка** может быть локальной или сетевой (UNC-путь `\\NAS\photos` или подключённый диск). Проверять доступность и права на запись перед стартом. Если папка недоступна, задание не запускается и пользователь видит понятное сообщение.
- **Первая синхронизация большой медиатеки** (ориентир — сотни гигабайт и десятки тысяч файлов) должна работать часами без роста памяти: ассеты обрабатываются потоком, а не загружаются списком целиком.
- Перечисление медиатеки: сначала посчитать, сколько новых файлов и сколько гигабайт предстоит скачать, показать это пользователю, затем качать.

### 6.5 Фоновая работа и трей

- Кнопки: «Запустить задание», «Пауза», «Остановить».
- Закрытие окна крестиком сворачивает в трей; полный выход — через меню трея.
- Не запускать вторую копию приложения (single instance); повторный запуск разворачивает уже открытое окно.

### 6.6 Интерфейс

**Главное окно:**

- Выбор активного аккаунта (выпадающий список) и статус сессии.
- Статус: «Ожидание», «Подсчёт новых файлов», «Загрузка», «Пауза», «Ошибка».
- Прогресс: файлов N из M, объём, скорость, оставшееся время, текущий файл.
- Блок запуска задания: период «с» / «по» и кнопка «Запустить» (подробнее в 6.7).
- Итог последнего запуска: скачано / пропущено / ошибок, кнопка «Показать ошибки».
- Кнопка «Открыть папку».

**Настройки** (вкладки):

- Корневая папка аккаунта (выбор через диалог, в нём же можно создать новую папку).
- Compact: включить/выключить, размер по длинной стороне, качество JPG (см. 6.3.1).
- Фильтры из 6.2.
- Параллельность, порог свободного места.

**Аккаунты:** список, добавить, переключить, выйти, удалить.

**Журнал:** последние записи лога с фильтром по уровню, кнопка «Открыть папку с логами».

**Трей:** иконка меняется по состоянию (ожидание / идёт загрузка / ошибка). Меню: Открыть, Пауза/Продолжить, Остановить, Выход. Уведомления Windows: задание завершено (с итогом), ошибка, нужен повторный вход.

### 6.7 Задание на период и продолжение после остановки

В первой версии загрузка работает только как задание на период. Пользователь указывает начальную и конечную дату, например с 01.01.2022 по 31.12.2023, и запускает загрузку кнопкой. Задание скачивает всё, что снято в этом периоде, и завершается. Одновременно выполняется только одно задание. Чтобы забрать новые фото, достаточно снова запустить задание на нужный период: уже скачанное будет пропущено.

Правила для дат:

- Обе границы включительные. «По 31.12.2023» означает до 23:59:59 31 декабря по времени съёмки.
- Попадание в период определяется по времени съёмки из метаданных, тем же правилом, что и раскладка по папкам в 6.3. Файл из периода всегда ложится в папку внутри этого периода. Предварительный отбор по дате из iCloud делать с запасом ±14 часов на границах, а окончательно решать по времени съёмки, чтобы не потерять снимки из дальних часовых поясов.
- Выбор дат через календарь. Быстрые варианты: «этот год», «прошлый год», «последние 30 дней», «весь период».
- Проверка ввода: начало не позже конца, иначе кнопка запуска неактивна и рядом подсказка.
- Перед запуском показать, сколько файлов и гигабайт попадает в период и сколько из них уже есть в корневой папке.
- Незавершённое разовое задание (параметры и прогресс) хранится в БД. При следующем запуске приложения предложить: «Продолжить задание 01.01.2022–31.12.2023? Скачано 4 120 из 9 800».
- iCloud отдаёт «Все фото» в порядке добавления, а не съёмки. Если библиотека умеет перечислять ассеты по дате съёмки, использовать это, чтобы прекращать перебор за границей периода. Если нет, перебирать всё и фильтровать на клиенте. Выбор записать в `DECISIONS.md`.

**Продолжение после остановки.** При повторном запуске после кнопки «Остановить», закрытия приложения, выключения компьютера или обрыва сети приложение делает следующее:

1. Получает из iCloud список ассетов, подходящих под текущие фильтры и период.
2. Для каждого вычисляет ожидаемый путь в корневой папке по правилам 6.3.
3. Сверяет его с БД и с тем, что реально лежит на диске. Файл считается скачанным, если он есть по ожидаемому пути и его размер совпадает с размером в iCloud.
4. Оставшиеся от прерванной загрузки `.part` удаляет и качает эти файлы заново.
5. Докачивает только недостающее.

Уточнения к сверке:

- Корневая папка считается источником правды, БД нужна для скорости. Если БД потеряна или повреждена, полная сверка по диску её восстанавливает.
- Если в БД файл отмечен как скачанный, а на диске его нет (удалён или перемещён вручную), по умолчанию он скачивается заново. В настройках есть опция «Не восстанавливать файлы, удалённые вручную».
- Если по ожидаемому пути лежит файл другого размера, его не перезаписывать и не удалять. Такой случай попадает в отчёт как конфликт, решение за пользователем.
- Сверка проверяет только наличие и размер, содержимое файлов не читает. На библиотеке в десятки тысяч файлов она должна занимать минуты.
- Compact сверяется отдельно. Если оригинал в Full size есть, а JPG-копии в Compact нет, копия создаётся из локального оригинала, без повторной загрузки из iCloud.

## 7. Нефункциональные требования

- **Безопасность:** пароль только в Windows Credential Manager; в логах не должно быть паролей, кодов 2FA, cookies и токенов (добавить фильтр в логгер и тест на него). Apple ID в логах маскировать (`al***@gmail.com`).
- **Конфиг:** `%APPDATA%\iCloudPhotoDownloader\config.json`, с версией схемы и миграцией при обновлении.
- **Логи:** `%LOCALAPPDATA%\iCloudPhotoDownloader\logs\`, ротация по размеру (5 × 10 МБ).
- **Ресурсы:** в простое не грузить CPU и сеть; во время загрузки окно остаётся отзывчивым.
- **Ошибки:** ни одно исключение не должно молча ронять приложение. Глобальный обработчик пишет в лог и показывает сообщение.
- **Обновление программы** поверх старой версии сохраняет настройки, аккаунты и БД состояния.

## 8. Сборка и установка

- Разработка и сборка идут на том же Windows-ПК, где будет работать программа: PyInstaller собирает .exe только под ту ОС, на которой запущен. Для сборки нужны Python 3.12 и Inno Setup. `build.ps1` проверяет, что они установлены, и подсказывает, что поставить (например через `winget`).
- `build.ps1` одной командой: создаёт venv, ставит зависимости, гоняет тесты, собирает PyInstaller по `packaging/app.spec`, затем установщик через Inno Setup (`ISCC.exe`).
- Результат: `dist\iCloudPhotoDownloader-Setup-<версия>.exe`.
- Установщик: установка в `%LOCALAPPDATA%\Programs\` (без прав администратора), ярлык в меню «Пуск», опционально на рабочем столе, корректная деинсталляция (удаляет программу, но не скачанные фото; спрашивает, удалить ли настройки).
- Версия программы в одном месте (`__version__`), подставляется и в exe, и в установщик.
- Иконка приложения и трея (несколько состояний) — простые, сгенерированные, без чужих логотипов, в том числе без логотипа Apple/iCloud.
- Exe будет без цифровой подписи, поэтому Windows SmartScreen покажет предупреждение при первом запуске. Упомянуть это в README.

## 9. Тестирование

Юнит-тесты (на `FakeICloudClient`, без сети):

- построение пути: часовые пояса, границы месяца/года, нет даты, конфликт имён, запрещённые символы, английские названия месяцев при русской локали Windows;
- БД состояния: повторный запуск не качает заново, восстановление после обрыва, «файл уже есть на диске»;
- фильтры: даты, типы, альбомы, Live Photos;
- `.part` → атомарное переименование, битый `.part` после сбоя удаляется и качается заново;
- в адаптере нет вызовов удаления;
- Compact: HEIC → JPG, поворот по EXIF Orientation, перенос даты съёмки и GPS, уменьшение по длинной стороне, конфликт имён, создание недостающей копии из локального оригинала без сети;
- в логах нет секретов.

Ручной сценарий на реальном аккаунте (чек-лист в `docs/MANUAL_TEST.md`): вход с 2FA, синхронизация небольшого диапазона дат, повторный запуск (0 новых), выдёргивание сети посреди загрузки, переключение аккаунта, закрытие приложения посреди задания и продолжение после перезапуска.

## 10. Критерии приёмки

1. Установщик ставит программу на чистую Windows 11 без Python.
2. Вход по Apple ID с 2FA работает, сессия переживает перезапуск программы.
3. Фото и видео за выбранный период лежат в `<выбранная папка>\ГГГГ\ММ Month\` (например `2023\03 March`) по времени съёмки из метаданных.
4. Повторная синхронизация без новых файлов в iCloud ничего не скачивает и занимает секунды-минуты, а не часы.
5. Прерванная синхронизация продолжается без дублей и битых файлов.
6. В iCloud ничего не удалено и не изменено.
7. Можно добавить второй Apple ID и переключиться на него; его файлы ложатся в корневую папку, выбранную для этого аккаунта.
8. Во время задания окно можно закрыть: загрузка продолжается в трее и заканчивается уведомлением.
9. Ошибки ADP / выключенного веб-доступа / истёкшей сессии показываются понятным текстом.
10. Задание с 01.01.2022 по 31.12.2023 скачивает ровно те файлы, что сняты в этом периоде по времени съёмки, и раскладывает их по папкам от `2022\01 January` до `2023\12 December`.
11. После остановки задания и повторного запуска приложение сверяет корневую папку и докачивает только недостающее. Файл из периода, удалённый вручную, скачивается снова.
12. В каждой папке месяца есть `Full size` с оригиналами и `Compact` с JPG-копиями всех фото (кроме DNG). Копии открываются стандартным просмотрщиком Windows без расширений, развёрнуты правильно и сохраняют дату съёмки.

## 11. Порядок работы для Claude Code

Работать этапами, после каждого этапа — рабочее состояние, тесты зелёные, коммит.

- **Этап 0. Проверка технологии.** Минимальный скрипт: вход + 2FA + перечислить 20 последних ассетов с датами + скачать 3 файла. Проверить актуальную версию `icloudpd`/`pyicloud_ipd`, как она работает как библиотека, где хранит сессию и отдаёт ли iCloud часовой пояс съёмки в метаданных ассета (см. 6.3). Записать выводы в `docs/DECISIONS.md`. Если вход не работает — остановиться и сообщить, не строить остальное.
- **Этап 1. Ядро.** Адаптер, движок, БД, построитель путей, CLI для отладки (`python -m ipd_app sync --account ... --from 2022-01-01 --to 2023-12-31 --dry-run`). Полное покрытие тестами из раздела 9.
- **Этап 2. GUI и трей.** Окна, диалог 2FA, запуск задания на период, уведомления, single instance.
- **Этап 3. Сборка.** PyInstaller spec, Inno Setup, `build.ps1`, README с установкой и требованиями к настройкам iCloud.

Общие правила:

- Не добавлять функций удаления ни в каком виде, даже «на будущее».
- Если требование противоречит тому, что реально умеет библиотека iCloud, — не выдумывать обходы, а описать проблему и варианты.
- Новые зависимости — только с обоснованием в `DECISIONS.md`.
